## 修复方案

### 问题 (a): `get_editor_screenshot` 在 `open_scene` 后返回旧帧

**根因**：`RenderingServer.force_draw()` 只刷新一次渲染命令队列，但编辑器的 3D/2D `SubViewport` 尚未将新场景的渲染命令入队。截图时读回的是旧场景的最后渲染帧。

**涉及文件**：`addons/godot_mcp/tools/editor_tools_native.gd`

**改动**：在 `RenderingServer.force_draw()` 后添加 `await RenderingServer.frame_post_draw`，等待一个完整的帧循环，确保 SubViewport 已完成新场景渲染。

```diff
	# Force a render flush so the viewport shows the current scene, not stale content
	RenderingServer.force_draw()
+	# Wait for the viewport to complete rendering the new scene on the next frame
+	await RenderingServer.frame_post_draw

	var texture: ViewportTexture = viewport.get_texture()
```

第 1202 行 `var texture: ViewportTexture = viewport.get_texture()` 之前插入。由于函数体内已有 `await` 调用（在 `_request_runtime_probe_poll` 等中），Godot MCP 框架支持协程式工具函数，无需改动函数签名。

### 问题 (b): `get_runtime_info` / `get_runtime_scene_tree` 在运行时场景切换后滞后

**根因**：`_extract_pending_runtime_probe_response` 中 fallback 循环静默返回任意 Cached 响应。对于没有 `match_fields` 的工具（`get_runtime_info`、`get_runtime_scene_tree`），`_payload_matches(payload, {})` 恒为 true，导致旧缓存被当作"成功"返回，阻止了轮询重试。

**涉及文件**：`addons/godot_mcp/tools/debug_tools_native.gd`

**改动 1** — `_extract_pending_runtime_probe_response` (第 2773-2794 行)

fallback 返回的缓存数据标记为 `"stale": true`，让上层知道数据不是新鲜的：

```diff
 	for message_name in response_messages:
 		var runtime_payload: Variant = bridge.get_latest_message_payload(message_name, match_fields)
 		if runtime_payload is Dictionary:
 			var response: Dictionary = runtime_payload.duplicate(true)
-			response["status"] = "success"
+			response["status"] = "stale"
+			response["stale"] = true
 			return response
 		if runtime_payload != null:
-			return {"status": "success", "value": runtime_payload}
+			return {"status": "stale", "stale": true, "value": runtime_payload}
```

**改动 2** — `_request_runtime_probe_poll` (第 2797 行起)

在轮询循环中，如果 `_request_runtime_probe` 返回 `"stale"`，继续轮询（而不是立即退出）。超时后才返回 stale 数据：

```diff
 	while Time.get_ticks_msec() < deadline_ms:
 		if tree:
 			await tree.process_frame
 		result = _request_runtime_probe(command, payload, response_messages, params, match_fields)
-		if result.get("status") != "pending":
+		if result.get("status") not in ["pending", "stale"]:
 			return result
+	# Timeout expired - return whatever we have (may be stale)
+	if result.get("status") == "stale":
+		result["status"] = "success"
+		result["from_cache"] = true
 	return result
```

这样保证：场景切换的短暂窗口期内，工具会持续轮询直到拿到新鲜数据；超时后才降级返回旧数据（标记 `from_cache: true`）。

**改动 3** — `_tool_get_runtime_info` (第 1609-1626 行)

现有 `"pending"` 的 stale 处理分支虽然不会触发（因为 inner fallback 截胡了），作为 defensive guard 保留，同时适配新的 `"stale"` 标记：

```diff
-	if result.get("status", "") == "pending":
+	if result.get("status", "") in ["pending", "stale"]:
```

**改动 4** — `_tool_get_runtime_scene_tree` (第 1721 行)

当前直接返回 `_request_runtime_probe_poll` 的结果，没有 stale 处理。改动 2 已确保 poll 超时前不会返回 stale 数据，所以无需额外改动。
