## 未通过/不稳定项分析

### 1.5 validate_script Autoload 感知 — ❌ 未通过

症状：`autoload_aware=false`, `valid=false`, error="Script has syntax errors"

**根因分析**：`_build_autoload_declarations()` 从 `ProjectSettings.get_property_list()` 读取 "autoload/" 前缀条目并生成 `var AutoloadName` 声明。但如果测试脚本内容中的 Autoload 引用名称与实际注册名大小写不匹配，或重试注入的声明格式与 GDScript 解析器期望不符，脚本仍然会验证失败。

**修复**（`script_tools_native.gd` ~L2077）：
1. 在 `_build_autoload_declarations()` 中增加调试日志，记录找到的 autoload 名称和注入的声明内容
2. 在重试失败路径中降级为更宽松的错误检测（当前已有 `_is_syntax_error_line` 启发式检测，但需要验证它是否正确过滤了 autoload 引用相关错误）

### 2.2 复杂表达式 + 截图超时 — ⚠️ 不稳定

症状：`OS.get_name()` 有时 pending，`get_runtime_screenshot` 多数 pending

**根因**：`_request_runtime_probe_poll` 的默认 timeout=1500ms 不足：
- 复杂表达式求值需要更多时间（特别是首次调用时 probe 需要建立完整通信链路）
- 截图数据量大，从游戏进程传输到编辑器进程需要更多时间

**修复**（`debug_tools_native.gd`）：
- 在 `_request_runtime_probe_poll` helper 中将默认 timeout 从 1500ms 提升到 **3000ms**（行 ~2801）
- 对所有 runtime 工具 schema 中的 `timeout_ms` 默认值从 1500 改为 3000

### N5: 调试器自动中断 — 新问题

症状：每次 `run_project` 后调试器自动进入 breaked 状态，需要额外 `debug_continue`

**根因**：MCPRuntimeProbe 作为 Autoload 启动时，`_ready()` 中调用 `EngineDebugger.register_message_capture("mcp", ...)` 和 `EngineDebugger.send_message("mcp:probe_ready", ...)`。Godot 调试器的默认配置可能在运行时捕获到 `register_message_capture` 时触发了断点（类似"引擎错误"断点）。

**初步诊断建议**：
1. 检查 `mcp_runtime_probe.gd` 的 `_ready()` 中是否有未捕获的异常
2. 在 `_ensure_debugger_capture_registered()` 中加 `push_warning()` 确认执行路径
3. 如果确实是调用 `EngineDebugger.send_message` 触发中断，可尝试延后发送时机

### N4: get_runtime_info stale 回退掩盖真实通信状态 — 低优先级

症状：get_runtime_info 总是返回 success（通过 stale/probe_ready 缓存回退），无法判断是否真正通信成功

**修复**：在 stale 回退结果中加 `"stale": true` 标记，让调用方知道数据来自缓存而非实时响应

### 1.8 find_script_symbol_references autoload_name 字段 — 待验证

症状：结果中无 `autoload_name` 字段

**根因**：`_build_autoload_path_map()` 在 `script_tools_native.gd` 中被 `_tool_find_script_symbol_references` 调用。需要验证该函数是否在引用搜索执行前正确初始化。可能是调用时序问题。

## 方案A实现：编辑器侧主动等待探针就绪信号（2026-05-17）

> 完整分析文档：`docs/debugging/runtime-probe-message-capture-latency-2026-05-17.md`

### 问题

复杂表达式（`OS.get_name()`）和截图（`get_runtime_screenshot`）持续返回 pending。根因是编辑器在探针完成 `EngineDebugger.register_message_capture()` 之前就发送了请求，消息到达游戏进程时没有 capture 处理器来接收。

### 解决方案

探针在 `_ensure_debugger_capture_registered()` 成功后已通过 `EngineDebugger.send_message("mcp:probe_ready", ...)` 发送就绪信号。方案A让编辑器侧 bridge 识别此信号，并在发请求前等待探针就绪。

### 修改内容

| 文件 | 修改 | 说明 |
|---|---|---|
| `mcp_debugger_bridge.gd` | 新增 `_probe_ready_session_ids: Dictionary` | 记录哪些 session 已收到 probe_ready |
| `mcp_debugger_bridge.gd` | `_capture()` 中识别 `mcp:probe_ready` | 收到消息后标记 session 就绪 |
| `mcp_debugger_bridge.gd` | `_setup_session()` 中重置 probe_ready | 新 session 启动时旧标志失效 |
| `mcp_debugger_bridge.gd` | 新增 `is_probe_ready(session_id)` | 查询指定 session 是否就绪 |
| `mcp_debugger_bridge.gd` | 新增 `wait_for_probe_ready(session_id, timeout_ms)` | 轮询等待就绪（最多 2 秒，每 50ms 检查一次） |
| `mcp_debugger_bridge.gd` | 新增 `reset_probe_ready(session_id)` | 重置就绪标志 |
| `debug_tools_native.gd` | `_request_runtime_probe_poll()` 开头新增等待 | 发请求前调用 `bridge.wait_for_probe_ready()` |

### 单元测试

在 `test/unit/test_mcp_debugger_bridge.gd` 新增 6 个测试：

|---|---|

**结论**：
1. ✅ 方案A成功消除了"请求在探针就绪前发出"的竞态问题，轻量级请求首次即成功
2. ❌ `OS.get_name()` / `Engine.get_frames_per_second()` 失败是 **GDScript Expression 类的引擎限制**，与消息捕获注册延迟无关
3. ⚠️ 截图/场景树等重量级请求仍有 1-2 帧异步延迟，这是 EngineDebugger 双进程通信的固有特性，无法进一步消除（但 `_request_runtime_probe_poll` 的重试机制可自动处理）
